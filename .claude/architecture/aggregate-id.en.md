# Aggregate ID Generation

> Who creates the ID, where, and how. For aggregates, see [tactical-ddd.md](./tactical-ddd.en.md); for saving, see [repository-pattern.md](./repository-pattern.en.md).

---

## 1. Core Principle — the ID Is Created by the Domain, Not the DB

```ts
// domain — the aggregate generates its own ID when it's born (before DB save!)
export class Article {
  private constructor(readonly id: string, ...) {}

  static create(authorId: string): Article {
    return new Article(generateId(), authorId);   // ← the domain generates the ID
  }
  static restore(props: { id: string; authorId: string }): Article {
    return new Article(props.id, props.authorId);  // ← keep the existing ID when restoring from DB
  }
}
```

The **exact opposite** of Spring/JPA's `@GeneratedValue(IDENTITY)` (DB auto-increment). The ID is created by the aggregate at `create` time, not by the DB.

---

## 2. Why the Domain Creates It

1. **Domain purity** — if the DB creates the ID, the aggregate is incomplete before save (no id) → the domain depends on the DB. If the domain creates it, the aggregate is complete even without a DB.
2. **ID needed before save** — to do other work (e.g. a cross-domain call) with that ID before saving, you need the ID in advance.
3. **Putting the ID in events** — to include the id in an `ArticleCreated` event, the ID must exist at create time.

---

## 3. `create()` vs `restore()`

- `create()` — a new aggregate. Generates a new ID.
- `restore()` — one loaded from the DB. Keeps the existing ID. Called by the repository's `toModel`.

---

## 4. Repository·TypeORM Receive the ID As-Is

```ts
// TypeORM entity — NOT @PrimaryGeneratedColumn (auto-generated)!
@Entity('articles')
export class ArticleEntity {
  @PrimaryColumn()   // ← just receives it. The DB doesn't create the ID
  id: string;
}
// repository mapper — save the domain ID as-is
private toEntity(a: Article): ArticleEntity {
  const e = new ArticleEntity();
  e.id = a.id;   // the ID the domain created, as-is
  return e;
}
```

---

## 5. ID Format — In One Shared Helper

Keep ID generation in one place, `common/generate-id.ts`. To change the format, replace only this function.

```ts
import { randomUUID } from 'node:crypto';

/** Defaults to UUID v4. If you need sortable IDs, replace just this function with uuidv7/ULID/cuid2. */
export function generateId(): string {
  return randomUUID();
}
```

- The default is dependency-free **UUID v4** (`node:crypto`).
- If you need a **sortable ID** (index benefit ordered by creation time), replace with **UUID v7 / ULID / cuid2**.
- **Don't use auto-increment** (conflicts with the domain-ID-generation principle + sequential-guessing security problem).

---

## 6. Background: auto-increment vs Generated ID (Rationale)

| | auto-increment | generated ID (UUID/ULID) |
|---|---|---|
| DB index performance | ✅ best (sequential) | UUIDv4 ▲ (random) / UUIDv7·ULID ✅ (sorted) |
| Domain can generate | ❌ (the DB creates it) | ✅ |
| Sequential-guessing security | ❌ vulnerable (IDOR) | ✅ safe |
| Distributed collision | ❌ | ✅ |

The reasons for using a generated ID are **①DDD (the domain generates the ID) ②security (guessing prevention)**. auto-increment is still valid for simple CRUD, but it conflicts with this template's DDD principles, so it's not adopted.

---

## 7. One-Line Summary

> The ID is generated by the domain aggregate at `create()` time (domain purity·pre-save reference·events), not by the DB (auto-increment). TypeORM receives it as-is via `@PrimaryColumn`. The format is managed in one place, `common/generate-id.ts`, defaulting to UUID v4 and swappable for a sortable ID when needed.
